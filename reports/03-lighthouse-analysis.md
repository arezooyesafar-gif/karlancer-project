# تحلیل سرعت با Lighthouse: zioma.ir

- تاریخ تست: ۹ مهر ۱۴۰۵
- ابزار: Lighthouse 13 داخل کروم، در حالت ناشناس (بدون ورود به حساب)

## ۱. وضعیت فعلی

| صفحه | دستگاه | امتیاز Performance | زمان پاسخ سرور (TTFB) | LCP | CLS |
|---|---|---|---|---|---|
| خانه | موبایل | **82** | 3.8 ثانیه | 3.2 s | 0 |
| دسته‌بندی (لوازم پخت‌وپز) | موبایل | **70** | **11.1 ثانیه** | 4.1 s | 0 |
| دسته‌بندی | دسکتاپ | **90** | 5.8 ثانیه | 0.8 s | 0.009 |
| محصول (آون توستر داتیس) | موبایل | **46** | 8.3 ثانیه | **7.9 s** | **0.288** |
| محصول | دسکتاپ | **84** | 9.0 ثانیه | 1.7 s | 0.012 |

TTFB یعنی مدتی که سرور طول می‌کشد تا اولین بایت صفحه را بفرستد. در یک سایت سالم با کش، این عدد زیر ۰٫۵ ثانیه است.

## ۲. یافته‌ها، به ترتیب اثر

### ۱) پاسخ سرور بسیار کند است: ۴ تا ۱۱ ثانیه برای هر صفحه

این مهم‌ترین مشکل است. در همهٔ تست‌ها بیش از ۹۰٪ زمان لود صرف انتظار برای HTML صفحه از سرور شده است. بقیهٔ فایل‌ها (CSS، JS، تصاویر و فونت‌ها) بعد از رسیدن HTML کمتر از ۱ ثانیه لود شده‌اند. تفکیک LCP صفحهٔ خانه این را نشان می‌دهد: از ۳٫۹ ثانیه، **۳٫۸ ثانیه** فقط انتظار برای سرور بوده است.

- **یعنی:** صفحه‌ها از کش LiteSpeed سرو نشده‌اند. یا کش صفحه خاموش است، یا این تست‌ها اولین بازدید بعد از پاک شدن کش بوده‌اند. باید با تست بخش ۵ مشخص شود.
- **راه‌حل اصلی:** روشن شدن کش صفحهٔ LiteSpeed. کش به‌خاطر باگ لوپ صفحه‌ها خاموش شده بود و اصلاحیه‌اش در mu-plugin است.
- **علت کندی خود PHP:** ساخت یک صفحه نباید ۴ تا ۱۱ ثانیه طول بکشد. تغییر زیاد این عدد بین صفحه‌ها نشان می‌دهد احتمالاً یک افزونه یا قالب هنگام ساخت صفحه به سرویسی خارج از ایران درخواست می‌فرستد و تا پایان مهلت (timeout) منتظر می‌ماند. امروز اتصال سرور با خارج قطع بود؛ من از بیرون نتوانستم به سایت وصل شوم. کش این مشکل را برای بازدیدکننده‌ها پنهان می‌کند، ولی سبد خرید، تسویه حساب و کاربرانِ واردشده همیشه بدون کش هستند. روش پیدا کردن علت در بخش ۵ آمده است.

### ۲) lazy-load افزونهٔ LiteSpeed تصویر اصلی را دیر لود می‌کند

- **صفحهٔ محصول:** تصویر اصلی محصول، که بزرگ‌ترین المان صفحه (LCP) است، توسط lazy-load افزونهٔ LiteSpeed تا اجرای JavaScript لود نمی‌شود. تأخیر روی موبایل **۳٫۴ ثانیه** و روی دسکتاپ **۵٫۷ ثانیه** است. علت اصلی LCP برابر ۷٫۹ ثانیه روی موبایل همین است.
- **صفحهٔ دسته‌بندی:** تصویر اولین کارت‌های محصول، که LCP موبایل است، همین وضعیت را دارد.
- **صفحهٔ خانه:** مشکلی ندارد. قالب خودش تصویر اسلایدر اول را از lazy-load مستثنا کرده است.

→ **اصلاح شد:** فایل `mu-plugins/zioma/lazyload.php` اضافه شد (بخش ۳).

### ۳) جابه‌جایی صفحه (CLS = 0.288) در صفحهٔ محصول موبایل

بعد از لود، کل بدنهٔ صفحهٔ محصول (`prk-product-page-shell`) جابه‌جا می‌شود. احتمالاً هدر مخصوص صفحهٔ محصول در موبایل بعد از لود ارتفاعش تغییر می‌کند. این مشکل فقط در موبایل و فقط در صفحهٔ محصول است. صفحهٔ خانه و دسکتاپ مشکلی ندارند. برای اصلاح بدون تغییر ظاهر، باید HTML همین صفحه را ببینم (بخش ۵).

### ۴) ۳۵ فایل CSS جدا که نمایش اولیه را متوقف می‌کنند

صفحهٔ خانه ۱۴۹ درخواست دارد: ۴۰ فایل CSS و ۶۰ فایل JS. حدود ۳۵ فایل CSS کوچک قبل از اولین نمایش لود می‌شوند. Lighthouse روی موبایل حدود ۱ ثانیه (در دسته‌بندی حدود ۲ ثانیه) صرفه‌جویی تخمین می‌زند، اگر این فایل‌ها یکی شوند (CSS Combine) و فشرده شوند (CSS Minify). یکی کردن ترتیب فایل‌ها را حفظ می‌کند و ظاهر نباید تغییر کند، ولی حتماً با مقایسهٔ اسکرین‌شات تست شود.

### ۵) فایل‌های JS و CSS هدر کش مرورگر ندارند

۵۹ فایل JS و CSS بدون مدت کش سرو می‌شوند، یعنی بازدیدکنندهٔ تکراری هر بار دوباره آن‌ها را دانلود می‌کند. تصاویر و فونت‌ها فقط ۷ روز کش می‌شوند. → با روشن کردن **Browser Cache** در LiteSpeed حل می‌شود و هیچ اثر ظاهری ندارد.

### ۶) موارد کوچک‌تر که عمداً دست نزدم

این موارد یا ظاهر یا کارکرد را عوض می‌کنند، یا تأیید کارفرما لازم دارند:

| مورد | اندازه | چرا دست نزدم |
|---|---|---|
| Google Analytics (gtag) | 157KB | تأخیر انداختنش ممکن است آمار بازدید را کم‌دقت کند. با تأیید کارفرما می‌شود انجامش داد. |
| دو کتابخانهٔ Swiper (قالب v11 و المنتور v8) | 78KB | حذف هرکدام ممکن است اسلایدرها را خراب کند. |
| فونت آیکون `pars-font.ttf` با فرمت TTF | 228KB | تبدیل به WOFF2 حدود ۶۰٪ کوچک‌ترش می‌کند و ظاهر عوض نمی‌شود، ولی خود فایل فونت را لازم دارم. |
| فونت آیکون Remix | 173KB | کوچک کردنش ممکن است بعضی آیکون‌ها را حذف کند. |
| تصاویر کارت محصول (768px برای نمایش 160px) | ~100KB در هر صفحه | تصویر کوچک‌تر روی صفحه‌های رتینا کمی تارتر دیده می‌شود. |
| Speed Index بالا (۸ تا ۱۸ ثانیه) | – | اسلایدرها و شمارنده‌های معکوس (تایمر تخفیف) دائم صفحه را تغییر می‌دهند و این عدد بالا می‌رود. حذفشان یعنی تغییر ظاهر. |

## ۳. تغییر کد در این مرحله

**`mu-plugins/zioma/lazyload.php`** (فایل جدید) و به‌روزرسانی **`zioma-performance.php`** و **`zioma/performance-config.php`**

این تغییر به LiteSpeed می‌گوید این تصاویر را lazy-load نکند:
- در صفحهٔ محصول: تصویر اصلی محصول
- در صفحهٔ فروشگاه و دسته‌بندی: تصویر ۴ محصول اول

تصویرها همان‌اند و همان‌جا نمایش داده می‌شوند. فقط دانلودشان زودتر شروع می‌شود. بقیهٔ تصاویر مثل قبل lazy-load می‌مانند. تعداد کارت‌ها در `performance-config.php` با `eager_product_cards` قابل تغییر است.

**تست انجام‌شده:** منطق تطبیق آدرس با کد خود LiteSpeed Cache (نسخهٔ گیت‌هاب) مقایسه و با آدرس‌های واقعی همین گزارش امتحان شد: تصویر اصلی محصول، نسخه‌های کوچک‌شده و نام‌های فارسی. تصاویر دیگر، مثل آیکون‌های خدمات، lazy می‌مانند.

## ۴. تنظیمات LiteSpeed Cache، به ترتیب

بعد از هر مرحله، Purge All بزنید. سپس خانه، یک دسته‌بندی و یک محصول را در **پنجرهٔ ناشناس**، روی موبایل و دسکتاپ، با اسکرین‌شات‌های قبل مقایسه کنید. اگر چیزی تغییر کرد، همان گزینه را خاموش کنید و به من خبر بدهید.

**مرحلهٔ A: بدون هیچ اثر ظاهری**

| بخش | گزینه | مقدار |
|---|---|---|
| Cache ← Cache | Enable Cache | ON |
| Cache ← Cache | Cache Mobile | ON |
| Cache ← Browser | Browser Cache | ON |
| Page Optimization ← Media | Lazy Load Images | ON (همان‌طور که هست) |

بعد از این مرحله، باگ لوپ صفحه‌ها را طبق بخش ۲ راهنمای `02-upload-and-test.md` تست کنید.

**مرحلهٔ B: فشرده‌سازی (ظاهر نباید تغییر کند، ولی مقایسه کنید)**

| بخش | گزینه | مقدار |
|---|---|---|
| Page Optimization ← CSS | CSS Minify | ON |
| Page Optimization ← CSS | CSS Combine | ON |
| Page Optimization ← JS | JS Minify | ON |

**این گزینه‌ها را روشن نکنید.** همه ظاهر صفحه را هنگام لود تغییر می‌دهند یا باعث پرش و جابه‌جایی می‌شوند:
- UCSS
- Load CSS Asynchronously
- Font Display Optimization
- Load JS Deferred یا Delayed
- HTML Minify (فاصلهٔ بین بعضی المان‌ها را تغییر می‌دهد و صرفه‌جویی‌اش ناچیز است)
- Guest Mode
- Guest Optimization
- Add Missing Sizes
- JS Combine

## ۵. چیزهایی که برای قدم بعد لازم دارم

1. **وضعیت کش:** در پنجرهٔ ناشناس صفحهٔ یک محصول را باز کنید. F12 را بزنید و به تب **Network** بروید، صفحه را **دو بار** رفرش کنید و روی ردیف اول (خود صفحه) کلیک کنید. در بخش **Response Headers** مقدار `server` و `x-litespeed-cache` را ببینید و اسکرین‌شات بفرستید. اگر `x-litespeed-cache` اصلاً وجود ندارد، یعنی کش صفحه کار نمی‌کند.
2. **mu-plugin:** در «افزونه‌ها» تب **«ضروری» (Must-Use)** را باز کنید و مطمئن شوید «Zioma Performance» آنجاست.
3. **علت کندی PHP:**
   - افزونهٔ رایگان **Query Monitor** را **موقتاً** نصب کنید. فقط برای ادمین دیده می‌شود.
   - به‌عنوان ادمین صفحهٔ یک محصول را باز کنید و از نوار بالای صفحه روی عدد زمان Query Monitor بزنید.
   - از بخش‌های **HTTP API Calls** و **Queries by Component** اسکرین‌شات بفرستید.
   - بعد از گرفتن اسکرین‌شات، افزونه را حذف کنید.
4. **برای CLS صفحهٔ محصول:** در پنجرهٔ ناشناس و در حالت موبایل (F12 و آیکون گوشی)، صفحهٔ محصول را باز کنید، Ctrl+S بزنید و «Webpage, HTML only» را ذخیره کنید. فایل را اینجا بفرستید.
5. اگر بشود، فایل `wp-content/themes/parskala/assets/fonts/parsfont/fonts/pars-font.ttf` را هم بفرستید تا نسخهٔ WOFF2 هم‌شکل و کم‌حجم آن را بسازم.

## ۶. انتظار واقع‌بینانه

- **دسکتاپ:** با روشن شدن کش و اصلاح lazy-load، دسته‌بندی و محصول باید به حدود **۹۵ تا ۱۰۰** برسند.
- **موبایل:** بیشترین بهبود را صفحهٔ محصول خواهد داشت (الان ۴۶). LCP آن از ۷٫۹ ثانیه به‌شدت کم می‌شود و بعد از اصلاح CLS بالاتر هم می‌رود.
- **سقف موبایل:** خانه و دسته‌بندی احتمالاً به **۸۵ تا ۹۵** می‌رسند. رسیدن به ۱۰۰ در موبایل بدون حذف اسلایدرها، تایمرها و آنالیتیکس (یعنی بدون تغییر ظاهر یا کارکرد) معمولاً ممکن نیست.

عدد دقیق بعد از هر مرحله با Lighthouse دوباره اندازه‌گیری و در گزارش نهایی قبل و بعد ثبت می‌شود.
