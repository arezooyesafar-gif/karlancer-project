# zioma.ir: speed optimization and bug fixing

Mirror of the server files we change on a WordPress + WooCommerce shop (theme: Parskala, with a child theme; cache: LiteSpeed Cache). The parent theme, plugins, uploads and core are not in the repo (see `.gitignore`).

## Client constraints

- The site must look exactly the same on mobile and desktop. SEO must not change.
- Back up before any significant change. Test on the client's test subdomain first.
- Put customizations in mu-plugins, never in the parent theme, so theme updates don't wipe them. The parent theme "پارس کالا" is the active theme, not the child; do not ask to switch themes (theme mods and menus are tied to the active theme).

## Layout

- `public_html/wp-content/mu-plugins/zioma-performance.php`: loader; site code is in `mu-plugins/zioma/`.
  - `performance-config.php`: per-context lists of style/script handles to dequeue, defer or preload. Find handles on the live site with `?zioma_assets=1` (admin only). Compare a page without the changes using `?zioma_perf=off`.
  - `asset-inspector.php`: the `?zioma_assets=1` bar; also records JS errors, failed files, Ajax/fetch requests, server stage timings, slow callbacks and hook-less stretches, outgoing HTTP calls, FCP/LCP, layout shifts (with the elements that changed height and the files that finished loading just before each one; the panel's own shifts and shifts after input are not counted), long animation frames with script attribution, theme version / wp_is_mobile / mu-plugins, the main query's paging numbers and the callbacks on query hooks, and on archives the `prk-av4` data attributes, paging/load-more markup, "یافت نشد" texts and IntersectionObserver targets; it copies everything as a text report the user pastes back. The panel summary shows the viewport width and mobile/DESKTOP so the user can check device mode.
  - `cache-compat.php`: keeps XHR requests out of the LiteSpeed page cache.
  - `lazyload.php`: excludes the main product image and the first product cards from LiteSpeed lazy-load (via `litespeed_media_lazy_img_excludes`).
  - `critical-css.php`: prints a small inline `<style>` at the top of `<head>` (from `critical_css_rules` in the config, obeying the `critical_css` mode) that pins layout-shifting elements to the state the theme's own scripts give them, so the page looks identical from first paint with no CLS. Now hides the `.prk-modal` overlays that otherwise sit in the mobile page flow until `prk-modal.js` runs.
  - `options-memo.php`: unserializes `memoize_options` (the theme's `prk_option`) once per request via `pre_option_*`; front end and Ajax only.
  - `plugin-filter.php`: drops `frontend_skip_plugins` (folders or files; Duplicator Pro, WooCommerce Advanced Bulk Edit) from `active_plugins` on visitor page views and wc-ajax only.
  - Both obey `server_tweaks` in the config: `off`, `trial` (only with `?zioma_trial=1`) or `on`.
  - Asset trims (`dequeue_styles` / `dequeue_scripts` in the config) obey `asset_trims` (`off` / `trial` / `on`; now `on`, the user confirmed identical appearance): wp-block-library on product and category pages, prk-reviews and prk-product-questions on home and category pages.
  - `delay-scripts.php`: output-buffer rewrite that turns `<script src>` tags matching `delay_scripts` (Google Analytics gtag.js; approved by the client) into placeholders loaded on first interaction or after `delay_timeout` seconds.
- `public_html/.htaccess`: our rules sit in the `# BEGIN Zioma` block, outside the WordPress and LiteSpeed blocks.
- `reports/`: audit and progress reports for the client (Persian). `06-final-report-draft.md` is the client-facing final report with blanks for the last measurements.
- The GitHub repo is public. Keep secrets in `wp-config.php` as `REMOVED`, and never commit the commercial parent theme, settings exports or HAR files (they can hold keys and session cookies).

## What we know about the live site

- zioma.ir (88.135.68.10, in Iran) resets connections from outside Iran, so this environment cannot open it. Data comes from the user: Lighthouse JSON from their Chrome, inspector reports, screenshots. Analysis: `reports/03-lighthouse-analysis.md`.
- WordPress 7.1.x, WooCommerce 10.9, Elementor 4.1, PHP 8.1.34, theme files under `themes/parskala/app/...`. LiteSpeed page cache works (`x-litespeed-cache: hit` on repeat views); cache misses take 4–11 s TTFB.
- The server cannot reach WordPress.org (plugin installs fail). Query Monitor on a category page (admin, uncached): 11.5 s total, 709 queries taking only 1.0 s, no WP HTTP API calls. So ~10 s is PHP work or raw network/DNS calls outside the WP HTTP API. First inspector report (cooking-equipment, admin, uncached, 34.6 s, 785 queries): plugins_loaded started at 4.4 s, init took 2.2 s, and wp_head→wp_footer (page body render) took 25.2 s. Second report (same page, Query Monitor still on, 20.5 s): OPcache on (99% hit), no persistent object cache; plugin loading ~4.3 s of which ~3.7 s is two hook-less stretches inside RTL-CareUnit (rtl-theme license manager; Storage.php then ORM.php, around options `22f91148…` and `rtl_rsm_localProducts`); init 2.4 s with `Prk\Woocommerce\MyAccountV4\MyAccountV4::register_endpoints` at 0.8 s; body render 12 s with no single stretch over 0.2 s.
- Third report (QM off): 40.2 s wall but only 9.0 s CPU (host CPU throttling suspected); 2,801 reads of `prk_option` cost 13 s (alloptions → option_prk_option); Duplicator Pro load 8.8 s (RTL-CareUnit license code runs inside it); `MyAccountV4::register_endpoints` 2.9 s. Write-up: `reports/04-server-diagnosis.md`.
- Trial comparison (cooking-equipment, admin): 40.3 s / CPU 8.5 s without tweaks, 19.7 s / CPU 4.2 s with `?zioma_trial=1`. The memo removed the 17 s of `prk_option` reads. Skipping Duplicator Pro moved the ~5 s RTL-CareUnit check to the next rtl-theme plugin (WooCommerce Advanced Bulk Edit), so it runs with whichever guarded plugin loads first; Bulk Edit was added to the skip list next.

- With tweaks on (cooking-equipment, admin, uncached): 5.2 s, 773 queries; remaining big item is Schema Pro's `schema_wizard` (1.6 s, RTL-CareUnit check inside). wc-ajax cart fragments take ~2 s per visit. Lighthouse runs so far were all cache misses; next step is keeping pages cached (LiteSpeed crawler) and re-testing on a second run. Fonts IRANYekanX Regular/DemiBold are preloaded via the config. Plan: `reports/05-speed-final-steps.md`.
- Lighthouse after LiteSpeed CSS combine + JS minify, gtag delay and font preload (`/washing-and-cleaning/dishwasher/sam-dishwasher/`, a brand subcategory with 2 products, so the footer is in the first mobile screen): desktop 99 (LCP 0.7 s, TBT 0, CLS 0.002); mobile 59 cached / 55 miss (FCP 2.2 s, LCP 2.8 s simulated; observed on the user's connection FCP 0.7 s, LCP 0.86 s, load 2.3 s). Mobile losses: TBT 1.3–1.8 s from ~11 observed tasks of 50–90 ms (×4 CPU in simulation), almost all "Other"/Unattributable rendering work, not script (scripting 350 ms); and CLS 0.161 = the Elementor footer (`.main-footer.mobit`) moving down ~272 px after first paint (something above it grows). They show `#search-modal-mobile` (858 px tall, with a 743 px banner image) in the page flow for ~100 ms around DOMContentLoaded before it is hidden (body +858 px, then back); on desktop that is below the fold, so no CLS. `prk-desktop-menu.js` does 23–49 ms of forced layout on DOMContentLoaded and moves `div.continer` down 6 px (CLS 0.047 in the admin view). cooking-equipment showed no Ajax request at all; whether the user scrolled is unknown. Mobile device-mode reports are still needed.
- getrusage() CPU is per PHP worker (LSAPI reuses workers), so the inspector reports CPU relative to when the mu-plugin loaded.
- Mobile device reports (real iPhone, uncached, 1 Oct 2026). Category (`cooking-equipment/stirrer/`): CLS 1.021. The killer shift (0.976) is the three mobile overlay modals — `#prk-av4-mobile-filter-modal`, `#prk-av4-mobile-sort-modal`, `#search-modal-mobile`, all `.prk-modal` — sitting in the page flow at full height (~1284+351+447 px) until `prk-modal.js` runs in the footer (~31 s cold), then collapsing to 0 and letting the footer render, shoving everything up. Fixed by inlining `html .prk-modal{display:none}` at the top of `<head>` via `critical-css.php` (the closed state the script settles them into; an open modal keeps its stronger selector). Smaller archive shifts: footer contact logo `<img>` with no dimensions (0.040) and the newsletter input restyled late (0.005). Product page (`...bm177`): CLS 0.277, almost all (0.274) from the tab sections `section#tab_specifications.product_tab` / `#tab_comments` rendering full then collapsing — needs the product-tabs template/JS to pin safely. LONG FRAMES on both pages are dominated by Elementor `common.min.js` (~730 ms blocking) and, on the product page, `product-gallery.js` (1019 ms script, 686 ms forced layout).
- Category result count bug (bug 2 family): on `cooking-equipment/stirrer/` the main query returns `found_posts 11, max_num_pages 1` (all 11 products fit one page; `loop_shop_per_page` is forced to 9999 by `prk_bbloomer_redefine_products_per_page`, so load-more is correctly absent here), yet `.prk-av4-result-count__value` shows "محصولی یافت نشد" with 11 cards visible.
- `archive-v4.js` has been read (kept out of git). It confirms: (a) the mobile filter/sort modals are rendered in the page flow and only moved into a body-level `.prk-modal-overlay` (display:none) on DOMReady via `mountArchiveModals()`, and a modal opens by getting `.show` + its overlay made visible (`PrkModal.openById`) — so the critical-CSS rule `html .prk-modal{display:none}` is confirmed safe (an open modal always wins on `.prk-modal.show`, stronger than the rule, and nothing measures a modal's height at init). The same `.prk-modal` overlay class covers the product page's `.prk-mobile-info-tabs-modal`, so the fix should also cut the product-page CLS. (b) The JS only swaps `[data-prk-av4-result-count]` on an Ajax filter (via `response.data.resultHtml`); the initial "محصولی یافت نشد" is server-rendered, so bug 2's visible defect is in the PHP result-count renderer (`ArchiveV4`), not this JS. Load-more itself is wired correctly here (button + IntersectionObserver, `data-has-more` authoritative), so the original "load more does nothing" needs a category with a real second page to reproduce.
- Product tab collapse (product-page CLS 0.274): `prk-product-tabs-content.css` (read, out of git) only shows the spec-table preview rule — `.specifications-content table.prk-native-attributes-preview:not(.is-expanded) tr.prk-native-attribute-row--initially-hidden{display:none}` (both breakpoints). If that preview/`is-expanded` state and the `--initially-hidden` row classes are present in the SSR HTML, the head CSS hides the extra rows with no shift; a shift means a script adds them late. The large `#tab_comments` collapse (1409→169) is the reviews list, not covered by that CSS. Need the JS that toggles the spec preview and the reviews/questions tabs to pin them safely — revisit after a product-page trial report shows what CLS is left once the `.prk-modal` fix lands.
- The inspector's SERVER section now shows wall vs CPU time, per-plugin load time, slowest stage-hook callbacks, hook-less stretches over 0.2 s, totals between consecutive hooks, and outgoing HTTP requests.
- Home `?zioma_assets=1` structure (admin, 2 Oct 2026). The homepage is one Elementor doc (`.elementor-1152`) with ~8 heavy carousel widgets, each with its own CSS+JS and a swiper instance: product_Multi_line, officals_carosel_v2, product_carosel, carousel_brands, item_category, swip_article_slider, mobile_grad_category, banner_ads. TWO swiper libraries load (Elementor `swiper-js` 140 KB + theme `swiper-bundle` 151 KB) plus `prk-smart-atc` 102 KB and remixicon font CSS 145 KB. NOTE the admin reports include editor-only Elementor JS (`elementor-common` 527 KB, app-loader, dev-tools, admin-bar) that a logged-OUT visitor does NOT load — consistent with the logged-out Lighthouse showing only 2.3 s script eval. So the real logged-out bottleneck is rendering the carousels + large DOM (Style & Layout), not JS. content-visibility is unsafe on the carousel sections (swiper measures 0 width on a skipped element and breaks), so it's limited to static below-fold blocks (footer). Home mobile CLS 0.180: `#search-modal-mobile.prk-modal` 395→0 (should be covered by the live `html .prk-modal` rule — a home report still showing this collapse means the fix wasn't deployed on that run), the mini-cart `.widget_shopping_cart_content` 602→0, and swiper `.slide-pre` cards collapsing on init. Conclusion: home mobile cannot reach 90 under Path A without lightening the homepage (fewer carousels / lighter widgets = visible change, client sign-off); realistic safe ceiling ~50–65. Category and product pages are lighter (no carousel stack) and will score higher.
- Real Lighthouse, home page, logged-out (2 Oct 2026): desktop 89 (FCP 0.6 s, LCP 0.7 s, TBT 130 ms, CLS 0.144); mobile 38 (FCP 2.8 s, LCP 3.5 s, TBT **10,850 ms**, CLS 0.182, SI 16.5 s, TTI 28.2 s, server 280 ms). So paint and server are fine; the mobile score is killed by TBT. The main-thread breakdown is the key: Style & Layout 11.3 s + Rendering 8.5 s + "Other" 17.8 s, but Script Evaluation only 2.3 s — the cost is laying out and painting a large DOM, not running JS, so script delay/trim barely helps. Opportunities: unused CSS ~134 KiB, unused JS ~75 KiB (both modest). The client chose the safe path (Path A: no visible change), accepting that mobile home realistically reaches ~55–70 this way and that 90+ would need a lighter homepage (visible change, client sign-off). The chosen lever is content-visibility:auto on below-the-fold containers (skips their layout/paint at load with no visual change), staged in critical_css_trial_rules starting with the footer; measure on `/?zioma_trial=1` in a logged-out Lighthouse run before widening. Reminder: `?zioma_assets=1` admin loads are instrumented + uncached and are NOT the score — judge speed only by a logged-out Lighthouse on a cached (or `?zioma_trial=1`) page.
