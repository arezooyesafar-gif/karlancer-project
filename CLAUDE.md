# zioma.ir: speed optimization and bug fixing

Mirror of the server files we change on a WordPress + WooCommerce shop (theme: Parskala, with a child theme; cache: LiteSpeed Cache). The parent theme, plugins, uploads and core are not in the repo (see `.gitignore`).

## Client constraints

- The site must look exactly the same on mobile and desktop. SEO must not change.
- Back up before any significant change. Test on the client's test subdomain first.
- Put customizations in mu-plugins, never in the parent theme, so theme updates don't wipe them. The parent theme "پارس کالا" is the active theme, not the child; do not ask to switch themes (theme mods and menus are tied to the active theme).

## Layout

- `public_html/wp-content/mu-plugins/zioma-performance.php`: loader; site code is in `mu-plugins/zioma/`.
  - `performance-config.php`: per-context lists of style/script handles to dequeue, defer or preload. Find handles on the live site with `?zioma_assets=1` (admin only). Compare a page without the changes using `?zioma_perf=off`.
  - `asset-inspector.php`: the `?zioma_assets=1` bar; also records JS errors, failed files, Ajax/fetch requests, server stage timings, slow callbacks and hook-less stretches, outgoing HTTP calls, FCP/LCP, layout shifts (with the elements that changed height and the files that finished loading just before each one; the panel's own shifts and shifts after input are not counted), long animation frames with script attribution, theme version / wp_is_mobile / mu-plugins, the main query's paging numbers and the callbacks on query hooks, and on archives the `prk-av4` data attributes, paging/load-more markup, "یافت نشد" texts and IntersectionObserver targets; it copies everything as a text report the user pastes back. The panel summary shows the viewport width and mobile/DESKTOP so the user can check device mode. Visitor recording: any logged-out page with `?zioma_cls=1` (e.g. run in PageSpeed Insights, so it measures exactly what PSI sees) records the same PAGE / LAYOUT SHIFTS / LONG FRAMES text and beacons it (at load and 0.7/1.5/2.5/4/7 s after, on pagehide and when hidden, since Lighthouse may close the page ~1–2 s after load; each send replaces the previous one for that view; nonce-checked, 60 KB cap; such pages are never cached by LiteSpeed so the recorder is always present; rejected sends are noted in `zioma_cls_rejected` and shown in the view; verified end-to-end with a local Lighthouse 12 run) as a POST to the home page `/?zioma_cls_report=1`, handled on `init` (not admin-ajax: a PSI run with the recorder on the page stored nothing and logged no rejection, so `/wp-admin/` is most likely closed to foreign IPs like PageSpeed's; a ping is also sent at DOMContentLoaded, and a broken head recorder is reported as such); the newest six are kept in the non-autoloaded option `zioma_cls_reports`, readable by admins as plain text at `/wp-admin/admin-ajax.php?action=zioma_cls_view` (`&clear=1` deletes them). Size changes listed under each shift leave out ancestors that only pass on a descendant's change. Each report ends the shift list with a STRUCTURE section for the element that moved most in each of the three largest shifts of 0.005 or more (shifts after input included, so a stray tap cannot hide one): its ancestors and the up to 8 elements before each, with first-seen height -> current height, top, and `data-layout*` / `data-prk-slider-settings` / `data-widget_type` attributes (* marks a change); up to 25 size changes are listed per shift; under each STRUCTURE, `inside <block>` outlines the two nearest changed blocks (widgets with `data-widget_type`, images with width/height attributes, natural and shown size, loading, and anything that changed height). Shifts under 0.001 print one line only. The PAGE section has a `zioma fixes on this page` line (head css, modal hold, banner layout, number of slider pins) so a report shows whether the latest files are live. A SLOW TIMER CALLBACKS section lists setTimeout/setInterval callbacks of 50 ms or more with the start of their code (the diagnostic views wrap both timers), because LoAF only reports inline timers as `TimerHandler:setTimeout @ page` and its `sourceCharPosition` is relative to the inline script, not the page.
  - `cache-compat.php`: keeps XHR requests out of the LiteSpeed page cache.
  - `lazyload.php`: excludes the main product image and the first product cards from LiteSpeed lazy-load (via `litespeed_media_lazy_img_excludes`).
  - `critical-css.php`: prints a small inline `<style>` at the top of `<head>` (from `critical_css_rules` in the config, obeying the `critical_css` mode) that pins layout-shifting elements to the state the theme's own scripts give them, so the page looks identical from first paint with no CLS. Now hides the `.prk-modal` overlays that otherwise sit in the mobile page flow until `prk-modal.js` runs. That plain rule loses to a stronger theme rule on product and home pages, so a second rule (now in `critical_css_rules['all']`, `on` after the user confirmed on trial that every product modal still opens) adds `html.zioma-modal-wait body .prk-modal.prk-modal:not(.show){display:none!important}` plus a tiny head script that sets `zioma-modal-wait` before first paint and removes it at `load`, or on the first pointerdown/touchstart/mousedown/keydown (capture phase) once the HTML is parsed (presses while `readyState` is `loading` are ignored: the theme only sets modals up at DOMContentLoaded). Tested in Chromium with a stronger theme rule, a fake prk-modal.js and a slow script: scrolling during load CLS 1.0 -> 0, a tap before or after DOMContentLoaded 0.358 -> 0, a modal opened after DOMContentLoaded still shows.
  - `options-memo.php`: unserializes `memoize_options` (the theme's `prk_option`) once per request via `pre_option_*`; front end and Ajax only.
  - `plugin-filter.php`: drops `frontend_skip_plugins` (folders or files; Duplicator Pro, WooCommerce Advanced Bulk Edit) from `active_plugins` on visitor page views and wc-ajax only.
  - Both obey `server_tweaks` in the config: `off`, `trial` (only with `?zioma_trial=1`) or `on`.
  - Asset trims (`dequeue_styles` / `dequeue_scripts` in the config) obey `asset_trims` (`off` / `trial` / `on`; now `on`, the user confirmed identical appearance): wp-block-library on product and category pages, prk-reviews and prk-product-questions on home and category pages.
  - `archive-count-fix.php`: on product archives, fixes `found_posts` when the host's server-level query cache (`wp-rand-prepend.php`: `mfm_search_pre` / `mfm_optimize_query`, a CloudLinux auto_prepend) leaves it at 0 (`archive_count_fix`), and removes those two hooks for product queries (`archive_loadmore_fix`) so real totals and pagination work. Both now also cover product queries in Ajax requests (admin-ajax is `is_admin()`), because the theme's category filters and load-more run over Ajax: with only page views covered, filters on paginated categories matched just the first page (client report, 4 Oct 2026).
  - `archive-infinite.php`: on product archives, turns on the theme's own Archive V4 load-more in its native scroll mode: it reads `prk_option['archive_v4_load_more_enable']` as on and `['archive_v4_load_more_mode']` as `'scroll'`. The live site had load-more off, so `LoopRenderer::render_load_more()` printed numbered pagination (`nav.prk-av4-pagination`, 1 2 3 4 بعدی); with it on, the theme prints an invisible 1 px trigger that its own IntersectionObserver (420 px ahead) and Ajax (`prk_archive_v4_load_more`, which our count fix covers) use to append the next `archive_v4_load_more_per_page` products, keeping filters and sorting. `/page/2/` URLs still work. Front end and Ajax only. Obeys `archive_infinite` (now `on`). The first version set only the mode, which did nothing while load-more was off; an earlier click-the-button script did not match the live markup either.
  - `slider-hold.php`: on `slider_hold_contexts` (front page), stops every running Swiper autoplay (`el.swiper.autoplay.stop()`, polled for 10 s so late inits are caught) and restarts it on the first touch/scroll/mouse/key or after `slider_hold_timeout` s, so carousels do not change slides during the load (PageSpeed mobile home: SI 8.0 s with the top slider changing slide mid-test). Obeys `slider_hold` (now `on`: PSI mobile SI 8.0 s → 5.2 s on trial). Tested with Swiper 11 and 8.
  - `slider-pin.php`: the theme's mobile image slider (`swip_article_slider`, `.prk-mobile-image-slider`) is server-rendered with full-width slides, and Swiper's side-peek start (slidesPerView >= 1.2, centred) narrows them, so the square image shrank 412->232 px on a 412 px phone and the whole home page below moved up 180 px (the 0.166 PSI shift on `.elementor-element-13473ac`; the slider container is `.elementor-element-752fc3a`). An output buffer adds a scoped `<style>` before each slider that lays out the not-yet-initialised slider exactly as Swiper will (slide width `(100% - (perView-1)*gap)/perView`, `margin-inline-end` gap, first slide centred with a wrapper translate, first slide's image ratio as `--prk-mobile-image-slider-frame-ratio`), read from the widget's own `data-prk-slider-settings` the way `buildSwiperOptions()` reads them; rules sit under `:not(.swiper-initialized)` and `@media (max-width:767.98px)` only; deferred (Ajax) sliders, non-slide effects, vertical and autoHeight sliders are skipped. Done in the page HTML, not `elementor/widget/render_content`, so Elementor's element cache cannot keep it. Tested in Chromium with the theme's real style.css/script.js on Swiper 8.4.7 and 11.2.10 at 375/412/430 px, including the theme's Elementor destroy-and-rebuild path: CLS 0.06–0.26 without, 0 with, identical geometry before and after start (only the loop's right peek and the active slide's title appear on start). With 1.75 per view and an 8 px gap the unpinned test reproduces the live numbers exactly (below-block 551->371, image 412->232). Obeys `slider_pin` (now `on`: report `zioma_cls=9` showed the slider container at 296 px from first paint and the user confirmed the slider looks and works the same).
  - `delay-scripts.php`: output-buffer rewrite that turns `<script src>` tags matching `delay_scripts` (Google Analytics gtag.js; approved by the client) into placeholders loaded on first interaction or after `delay_timeout` seconds. The loader goes before `</body>`, or at the end of the buffer when another plugin closed it early: the client's `omid.php` used to `ob_end_flush()` whatever buffer was on top at `wp_footer` 999 on every page, which was this one, so on every page except mobile home GA's tag was replaced but its loader never printed (GA likely not loading there until the fixed `omid.php` and this change are live).
- `public_html/.htaccess`: our rules sit in the `# BEGIN Zioma` block, outside the WordPress and LiteSpeed blocks: XHR requests bypass the LiteSpeed page cache, and static files (css/js/fonts/images/video, matched by extension so HTML/PHP/JSON are never affected) get `Cache-Control: public, max-age=31536000` whatever LiteSpeed's Browser Cache setting is (earlier Lighthouse runs showed JS/CSS with no cache lifetime and fonts with 7 days). The user pastes only the new lines into the server file, never the whole file.
- `reports/`: audit and progress reports for the client (Persian). `06-final-report.md` is the client-facing final report (filled in with the 4 Oct 2026 PageSpeed results).
- The GitHub repo is public. Keep secrets in `wp-config.php` as `REMOVED`, and never commit the commercial parent theme, settings exports or HAR files (they can hold keys and session cookies).
